一、研究摘要

核心结论：ecompass 应定位为「项目主管 Agent」（Supervisor），不变大只变聪明，变大的是 specialist 池（validation-lab、launch-prep 等）。通过标准化的 inbox/artifact 协议实现任务分发与结果整合。

  • main = 用户入口
  • ecompass = 项目主管（Supervisor）
  • specialists = validation-lab / launch-prep / [future]
  • 通信介质 = inbox 文件 + sessions_send

ecompass 作为 Supervisor 的职责

  • 任务拆解 — 复杂任务拆成子任务
  • 路由分发 — 判断类型，发给对的 specialist
  • 结果整合 — specialist 输出整合成结论
  • 决策升级 — 跨维度/不可逆问题上报用户

ecompass 不应该做的事

  • ❌ 自己做市场验证 → 交给 validation-lab
  • ❌ 自己渗透 Reddit → 交给 launch-prep
  • ❌ 天天管执行细节 → 让 specialist 自跑
  • ❌ 变臃肿万金油 → 保持专注，只做路由

三、三大 Agent 协调模式对比

⭐ Supervisor Pattern — 推荐方案
Supervisor（主管模式）
中央 supervisor 只负责调度和整合，不做具体执行；每个 worker agent 是独立专家；任务完成后汇报给 supervisor 汇总。
代表：AutoGen Supervisor / CrewAI Hierarchical 适用：复杂任务 · 多专业协作 · 企业级
Chain（链式模式）
线性流程，Agent A → Agent B → Agent C，后一步依赖前一步输出。
代表：LangGraph 状态机 弱点：不适合有分支/判断的流程
Router（路由模式）
一个中央 agent 做分类决策，把任务分发到对应 specialist，不做执行。
代表：LangChain LCEL Router 弱点：不做执行时，整合能力偏弱

八、运营原则

  • ✅
    ecompass 不变大，变聪明；变大的是 specialist 池
    每个 specialist 独立可启动，职责边界清晰
  • ✅
    通过 inbox 文件通信，不直接互相调用
    所有任务下发/回报经过结构化 JSON 文件，可追溯
  • ✅
    specialist 无任务时静默，不发无效心跳
    只有 running/blocked 状态才触发汇报
  • ✅
    ecompass 做判断层，不做执行层
    市场验证→validation-lab；预热运营→launch-prep；内容→content-agent
  • ❌
    不建臃肿单一 agent
    当 specialist 职责越来越多时，应该拆分出新的 specialist，而不是塞进 ecompass
  • ❌
    不越界执行 specialist 职责
    如果 ecompass 收到市场验证任务，应该转发给 validation-lab，而不是自己跑
